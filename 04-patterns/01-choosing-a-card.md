# 01 · เลือกการ์ดให้ถูกใบ

**ชั้น 04** · Marketplace Patterns

รวมการตัดสินใจที่กระจายอยู่ใน §1 ของ 8 ไฟล์ในชั้น 03 ไว้ที่เดียว

---

## 1 · ตารางตัดสินหลัก

เริ่มจาก **สิ่งที่ผู้ใช้กำลังเลือก** ไม่ใช่จากชื่อหมวดในระบบหลังบ้าน

| ผู้ใช้กำลังเลือกอะไร | การ์ด | ตัวชี้ขาด |
|---|---|---|
| ของที่จับต้องได้ | [`ProductCard`](../03-components/src/marketplace/ProductCard.md) | มีหน่วยนับและจำนวนสั่งขั้นต่ำ |
| งานที่มีคนทำให้ | [`ServiceCard`](../03-components/src/marketplace/ServiceCard.md) | มีรูปแบบการคิดเงิน 5 แบบ |
| **เงินที่ไม่ต้องคืน** | [`GrantCard`](../03-components/src/marketplace/GrantCard.md) | ทุน · เงินอุดหนุน · เงินร่วมจ่าย |
| **เงินที่ต้องคืนเงินต้น** | [`FundingCard`](../03-components/src/marketplace/FundingCard.md) | สินเชื่อทุกชนิด **รวมดอกเบี้ย 0%** |
| สิ่งที่รัฐให้ที่ไม่ใช่เงิน | [`ProgramCard`](../03-components/src/marketplace/ProgramCard.md) | ที่ปรึกษา · จับคู่ · พาออกงาน · การรับรอง |
| หลักสูตรที่มีกำหนดการ | [`TrainingCard`](../03-components/src/marketplace/TrainingCard.md) | มีวันเริ่ม–จบ และที่นั่ง |
| **ธุรกิจหนึ่งราย** | [`BusinessCard`](../03-components/src/marketplace/BusinessCard.md) | ไม่มีราคา — คือตัวคู่ค้าเอง |
| โปรไฟล์เต็มของผู้ขาย | [`SellerProfile`](../03-components/src/marketplace/SellerProfile.md) | ใบรับรองทั้งชุด + ข้อมูลภาษี |

**ไม่ใช่การ์ดในมาร์เก็ตเพลส** → `<Card>` ธรรมดา · **แถวในตาราง** → `<CompareTable>` · **สรุปตัวเลขที่กดไม่ได้** → `<Stat>` (ยังไม่มี)

> ⚠️ **ห้ามเรียก `<EntityCard>` ตรง ๆ ในหน้าแอป** — เรียกได้เฉพาะตอนสร้าง domain card ใบใหม่ · wrapper คือสิ่งที่รู้ว่า label ของจำนวนเงินคืออะไร ซึ่งเป็นทั้งหมดของความปลอดภัยในการ์ดกลุ่มนี้

## 2 · ★★★ เงิน: `GrantCard` หรือ `FundingCard`

การตัดสินใจที่ผิดแล้วแพงที่สุดในระบบ

```
                  ผู้รับต้องคืนเงินต้นหรือไม่
                              │
              ┌───────────────┴───────────────┐
            ไม่คืน                          คืน
              │                               │
         GrantCard                      FundingCard
              │                               │
     ทุน · เงินอุดหนุน            สินเชื่อทุกชนิด รวม 0%
     เงินร่วมจ่าย 50%             ทุนที่มีเงื่อนไขคืน
                                  สินเชื่อที่ยกหนี้ได้

              ไม่แน่ใจ ──────────► FundingCard
```

### เกณฑ์ที่พิจารณาแล้วและทิ้ง

| เกณฑ์ | พังที่เคสไหน |
|---|---|
| "มีดอกเบี้ยไหม" | สินเชื่อ 0% กลายเป็นทุน — **ความผิดพลาดที่แพงที่สุดที่เป็นไปได้** |
| "ผู้ออกเป็นแบงก์หรือหน่วยงาน" | ทุน BOI ที่จ่ายผ่านธนาคารของรัฐกลายเป็นสินเชื่อ |

### ทำไม "เมื่อไม่แน่ใจ" ถึงเอนไปทาง `FundingCard`

เป็นการเลือก**ทิศทางของความผิดพลาด**อย่างตั้งใจ ไม่ใช่ความขี้เกียจ

> เห็น "ทุน" แล้วรู้ทีหลังว่าเป็นหนี้ — เสียหายกว่า
> เห็น "สินเชื่อ" แล้วรู้ทีหลังว่าไม่ต้องคืน

วิธีเดียวกับที่ `Badge.md` ปิดทางที่เสียหายกว่าด้วยกฎ *"ทองไม่ใช่สถานะ"*

## 3 · คู่ที่สับสนบ่อย

| คู่ | ตัวชี้ขาด | เคสตัวอย่าง |
|---|---|---|
| `ProductCard` ↔ `ServiceCard` | **มีของส่งมอบไหม** | โปรแกรมบัญชีซื้อขาด → `ProductCard` (`unit="ไลเซนส์"`) · วางระบบ ERP → `ServiceCard` |
| `ServiceCard` ↔ `TrainingCard` | **มีกำหนดการและที่นั่งไหม** | ที่ปรึกษาตัวต่อตัว → `ServiceCard` · workshop 2 วัน → `TrainingCard` |
| `ProgramCard` ↔ `GrantCard` | **ผู้สมัครได้เงินไหม** | พาไปออกงาน → `ProgramCard` · เงินอุดหนุนค่าบูท → `GrantCard` |
| `ProgramCard` ↔ `TrainingCard` | **แกนกลางคืออะไร** | โครงการที่มีอบรมเป็นส่วนหนึ่ง → `ProgramCard` · หลักสูตรล้วน → `TrainingCard` |
| `BusinessCard` ↔ `SellerProfile` | **อยู่ในลิสต์หรือเป็นทั้งหน้า** | ผลจับคู่ในกริด → `BusinessCard` · หน้าโปรไฟล์ → `SellerProfile` |
| `BusinessCard` ↔ `ProgramCard` | **ธุรกิจ หรือ โครงการ** | ซัพพลายเออร์ที่ระบบเสนอ → `BusinessCard` · โครงการจับคู่ของ สสว. → `ProgramCard` |

## 4 · ★ ไม่มีการ์ดตามหมวดสินค้า

**หมวดสินค้าไม่ใช่เหตุผลที่จะสร้างการ์ดใหม่** — ถ้าสร้าง `SolutionCard` สำหรับซอฟต์แวร์ ก็ต้องมี `LogisticsCard` `PackagingCard` ตามมาไม่จบ ทั้งที่ทั้งหมดคือสินค้าหรือบริการอยู่ดี

เกณฑ์เดียวที่ควรสร้าง wrapper ใหม่ (`EntityCard.md §3`): **ความหมายของ `amount` ต่างจากที่มีอยู่**

| อยากได้การ์ดสำหรับ | ที่จริงคือ |
|---|---|
| ซอฟต์แวร์ซื้อขาด | `ProductCard` `unit="ไลเซนส์"` |
| SaaS รายเดือน | `ServiceCard` `pricingModel="per-month"` |
| งานวางระบบ | `ServiceCard` `pricingModel="per-project"` หรือ `"quote"` |
| ขนส่ง · คลังสินค้า | `ServiceCard` |
| บรรจุภัณฑ์ | `ProductCard` |

**ช่องว่างที่แท้จริงของซอฟต์แวร์คือ *รูปแบบการจ่าย* ไม่ใช่ *หมวด*** — และแก้ไปแล้วด้วย `per-month`/`per-year` ใน `ServiceCard`

---

## 5 · การสร้างการ์ดใบใหม่ — เมื่อไรถึงจะสมเหตุสมผล

ต้องผ่านทั้ง 3 ข้อ

1. **`amount` มีความหมายที่ยังไม่มีใครใช้** — หรือไม่มี `amount` เลยแบบ `ProgramCard`/`BusinessCard`
2. **มี prop ที่บังคับความถูกต้องได้** ซึ่งการ์ดอื่นไม่มี — เช่น `coPaymentPercent` ของ `GrantCard` · `collateral` ของ `FundingCard`
3. **เส้นแบ่งกับการ์ดที่มีอยู่เขียนเป็นประโยคเดียวได้** และตัดเคสก้ำกึ่งจริงได้ 3–4 เคส

ถ้าผ่านไม่ครบ ให้ขยายการ์ดเดิมแทน (แบบที่ `ServiceCard` ทำกับ subscription)

**วิธีสร้าง:** ดู `EntityCard.md §8` ซึ่งมีตัวอย่างเต็มของ wrapper ใหม่

## 6 · ❌ / ✅

| ❌ | ✅ | ทำไม |
|---|---|---|
| `<GrantCard>` กับสินเชื่อดอกเบี้ย 0% | `<FundingCard>` | ยังต้องคืนเงินต้น |
| `<EntityCard>` ตรง ๆ ในหน้าแอป | wrapper ตัวใดตัวหนึ่ง | wrapper รู้ว่า label ของเงินคืออะไร |
| สร้าง `SolutionCard` สำหรับซอฟต์แวร์ | `ProductCard` หรือ `ServiceCard` | หมวดสินค้าไม่ใช่เหตุผลที่จะมีการ์ดใหม่ |
| สร้าง `FundingCard` ที่ wrap `GrantCard` เฉย ๆ | ขยาย `GrantCard` แทน | wrapper ที่ไม่เพิ่มความหมายคือช่องให้หยิบผิดตัว |
| `<BusinessCard>` ในหน้าโปรไฟล์ผู้ขาย | `<SellerProfile>` | การ์ดไม่มีที่ให้ใบรับรองทั้งชุดและข้อมูลภาษี |
| ปล่อยเคสก้ำกึ่งให้แต่ละคนตัดสินเอง | เขียนไว้ในตาราง §2–3 | ระบบไม่สม่ำเสมอ = ผู้ใช้เรียนรู้ใหม่ทุกหน้า (A3) |
